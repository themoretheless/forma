# Бенчмарки Forma и план оптимизации

Результаты последовательных изменений: [OPTIMIZATION_STEPS.md](OPTIMIZATION_STEPS.md).
Таблица ниже сохраняет исходный baseline для сравнения, не последнюю скорость.

## Baseline: 6 сентября 2026, Apple M5 / Metal

24 GiB общей памяти, 10 логических CPU; release, 3 независимых процесса на
сценарий. Значения ниже — медианы. Renderer не оптимизирован в этом изменении:
добавлены измерители и тестовые сценарии.

| GPU-сценарий | Offscreen кадры/с | Completed p95 | GPU pass mean | CPU, один core=100% | alloc+realloc / кадр | RSS после серии |
|---|---:|---:|---:|---:|---:|---:|
| Кнопка, 800×400 | 633 | 1.60 ms | 0.69 ms | 13.5% | 43.25 | 18.58 MiB |
| Кнопка, 1920×1080 | 306 | 3.67 ms | 2.02 ms | 13.7% | 43.25 | 18.77 MiB |
| Кнопка, 3840×2160 | 208 | 6.46 ms | 4.23 ms | 12.1% | 43.25 | 18.89 MiB |
| Resize target около 4K | 118 | 12.21 ms | 4.08 ms¹ | 36.5% | 8475.67 | 19.84 MiB |
| 40 текстовых блоков, 1920×1080 | 72 | 14.95 ms | 11.89 ms | 3.7% | 43.25 | 22.17 MiB |
| Те же блоки + 12 clip, 1920×1080 | 29 | 36.24 ms | 31.88 ms | 1.6% | 43.00 | 22.22 MiB |

¹ Отдельный статический pass последнего размера, без создания target; подробнее ниже.
Это не частота кадров экрана. GPU time и completed latency собраны в разных
фазах; они не обязаны складываться с CPU submit в точное равенство. Серии
не изолированы от нагрузки ОС/DVFS: например, 4K throughput между повторениями
меняется, для регрессионных выводов нужны дополнительные прогоны на той же машине.

В 4K у кнопки учтено 0.21 MiB GPU-буферов и 31.64 MiB payload одного target;
у текстовой сцены в 1080p — 1.10 MiB буферов и 7.91 MiB target. Это не общая
VRAM и не число, которое можно прибавить к RSS. При обычной анимации наши
геометрические буферы не пересоздаются; 43 вызова heap на кадр включают wgpu.
При resize трафик Rust allocator около 778 KiB/кадр. Это трафик, не утечка.

CPU fallback кнопки в 4K: 436 offscreen кадров/с, p95 2.67 ms, около 100% одного
core, RSS 42.95 MiB; **не включает загрузку host buffer на экран**. Его нельзя
объявлять быстрее GPU-приложения по этим числам: отличается завершение pipeline.
Он также создаёт примерно 1.21 MiB allocation traffic на кадр анимации.

Основной вывод: для текста/clip ограничивает GPU-работа, при resize — ещё и
тысячи CPU-аллокаций. Просто менять backend или увеличивать число кадров в очереди
не устраняет эти причины.

**Native window FPS в этом запуске недоступен.** Три попытки измерения не дали
ни одного успешного surface acquire/present. В последней: 341 `Occluded`, 0
success/timeout/outdated; перед выходом окно `visible=true`, `focused=false`,
800×400 физических пикселей при DPI 2. Причина состояния ОС не установлена.
Это не результат «приложение работает с 0 FPS». Тестовый executable и команда
готовы для запуска в активной GUI-сессии; ошибка сохранена в `window-failure.json`.
Offscreen-результаты выше от этого не зависят и не подменяют оконный замер.

## Запуск

Требуются Node, Cargo, закешированные Rust-зависимости и настоящий GPU.
Отсутствующий adapter — ошибка, не успешный пропуск.

```sh
node scripts/perf-bench.mjs .forma/perf/my-run
node scripts/window-bench.mjs .forma/perf/my-run
```

Вторая команда открывает временные нативные окна, каждое закрывается само.
Не перекрывайте их другими окнами. До начала серии выключите другие GPU-нагрузки;
запускайте offscreen и window серии последовательно, а не параллельно.
Выходные файлы: `metadata.json`, `results.json`, `REPORT.md`, `windows.json`.
Все они локальные, под игнорируемой `.forma/`; текущий виртуальный проект Studio
не меняется. Сцены генерируются из версионируемых примеров и кода скрипта.

По умолчанию offscreen: 3 отдельных процесса на сценарий, 20 кадров прогрева,
120 измеряемых кадров. Можно задать `FORMA_BENCH_REPEATS` и `FORMA_BENCH_FRAMES`.
Native window: 1 секунда прогрева + 5 секунд измерения, 3 процесса на размер.
Настройки: release, DPI 2 для offscreen; фактический DPI/размер для окна.
Результаты разных backend/ОС требуют отдельных прогонов; браузер/WebGPU здесь
не измеряется. Сам UI runtime пока содержит одну кнопку с составным содержимым,
а не произвольное дерево из тысячи интерактивных контролов.

Сравнение полных серий проверяет одинаковые сцены, DPI, число повторений,
машину и SHA-256 всех `.ui`:

```sh
node scripts/compare-bench.mjs .forma/perf/before .forma/perf/after
```

Для дополнительной проверки временного дрейфа сохраните два release executable
`perf_bench` до/после изменения и запускайте их попарно:

```sh
node scripts/interleave-bench.mjs /path/to/before /path/to/after \
  .forma/perf/fixtures .forma/perf/paired
```

Скрипт не собирает код во время измерений: 6 GPU-сценариев × 4 пары,
по 240 кадров, сбалансированный порядок AB/BA. Хеши executable и fixtures,
порядок запусков, raw results и наблюдаемые диапазоны сохраняются в отчёт.
Это снижает влияние медленного дрейфа, но не изолирует машину от фоновой нагрузки.

## Что именно измеряется

- `render_throughput_fps`: кадры/с в последовательном offscreen цикле с ожиданием
  GPU после каждого кадра. Не FPS монитора, не максимальная конвейерная пропускная
  способность. CPU fallback включает запись в заранее выделенный XRGB host buffer,
  но не загрузку/present этого буфера; напрямую сравнивать это как FPS приложения нельзя.
- Native `present_calls_per_second`: частота успешных вызовов present в настоящем
  окне с FIFO и той же настройкой Metal-транзакций, что у приложения. Это ближе к
  поведению приложения, но не доказательство числа уникальных кадров на scanout.
- CPU submit, completed и интервалы окна: p50/p95/p99; в summary — медианы
  статистик трёх процессов, не процентили объединённой выборки.
- CPU: `getrusage`, сумма user+system всех потоков; 100% — один полностью занятый
  логический CPU. Счётчик включает Rust-часть wgpu, не только код Forma.
- Аллокации: успешные вызовы Rust `GlobalAlloc`; alloc/realloc/dealloc, суммарный
  запрошенный объём, живые байты и пик. Объём трафика не равен одновременно занятой
  памяти. Objective-C/Metal/mmap и bookkeeping системного allocator сюда не входят.
  Счётчики атомарные и сами имеют небольшую стоимость; снимки не транзакционны.
- RAM: текущий RSS процесса до/после серии; отдельно high-water за жизнь процесса.
  Это не пик RSS строго внутри измеряемой фазы и не сумма Rust allocations.
- GPU: живые размеры принадлежащих Renderer буферов, их число, создание/загрузки.
  Payload одного RGBA8 target = ширина × высота × 4; не включает выравнивание,
  другие swapchain images, pipeline, driver heaps и staging.
- На Apple Silicon память общая: RSS нельзя складывать с GPU payload и называть
  результат VRAM. Полная driver residency/VRAM usage здесь **недоступна**.
- GPU timestamps: отдельная профилирующая серия из 30 кадров, после основной
  CPU/allocator фазы. Обычный Renderer не включает queries. Сначала дожидаемся
  render submission, затем отдельным submission resolve/readback: на проверенном
  Metal немедленный resolve в том же submission давал устаревший end timestamp.
  Неверная/неполная серия становится `null`, а не огромным wraparound-числом.
  Это время render pass, не всего resize, present или readback.

`resize` меняет размер **target**, оставляя логическую сцену фиксированной;
создание нового target включено в основной интервал. Отдельные GPU timestamps
этой строки относятся к статическому последнему размеру, не ко всей resize-серии.
`forced` намеренно рисует неизменную сцену каждый кадр для измерения стоимости.
Настоящее приложение в покое не обязано рисовать: synthetic `idle` не вызывает
рендер и служит baseline процесса, но не проверяет wakeups оконного event loop.

## Исходный план оптимизации

Ниже описаны причины, выявленные в baseline. Статус выполненных изменений
и отдельные бенчмарки каждого этапа — в [OPTIMIZATION_STEPS.md](OPTIMIZATION_STEPS.md).

1. **Тайлы и clip.** `DisplayList::tiles` создаёт `Vec<Vec<u32>>` по числу тайлов;
   каждый push/pop clip попадает во все тайлы viewport. Для 4K это 8160 тайлов.
   Перейти к count → prefix sum → fill в переиспользуемых плоских массивах;
   отсекать целые группы по пересечению clip и bounds содержимого. Сохранять
   painter order и парность групп. Это затрагивает и CPU resize, и GPU пустых областей.
2. **Переиспользование GPU-буферов.** Ёмкость с запасом, обновление `COPY_DST`,
   новые bind groups только при росте capacity. Ключ tile grid — ceil(size/32),
   а не каждый отдельный размер пикселя, если геометрия/DPI не менялись.
3. **Версия геометрии.** Сейчас каждый draw сравнивает массивы commands/edges
   целиком и хранит их копии. Нужен стабильный identity + geometry revision,
   не один указатель на объект. Изменение цвета должно обходиться проверкой O(1).
4. **Освобождение ненужного CPU-кэша.** Web-preview сначала может рисовать CPU,
   затем перейти на GPU и оставить растровый кэш в том же Button. Освобождать
   его после успешного GPU-кадра, восстанавливать лениво при fallback.
5. **Scroll и glyph cache.** Сейчас scroll перестраивает display list и контуры
   текста. Хранить локальную геометрию, менять transform/clip; кэшировать контуры
   glyph по шрифту и допуску. Это более крупный архитектурный этап.
6. **Мелкие аллокации.** Native uniform-параметры — `[f32; 12]`, а не растущий Vec;
   hit-test/viewport — фиксированные массивы. Это полезно, но не заменяет пункты 1–2.

До изменения renderer зафиксирован baseline. Не ускорять resize отменой синхронного Metal present: это может
вернуть визуальное «плавание». Не снижать качество AA ради красивых чисел.

## Критерии следующего сравнения

- Нулевые загрузки неизменной геометрии при анимации.
- Число аллокаций resize перестаёт расти пропорционально числу тайлов.
- Buffer capacity/память достигают плато при повторном grow/shrink, без накопления.
- Прогресс отдельно по CPU submit, GPU-pass и window p95, а не одному среднему FPS.
- Pixel-regression для nested/translucent clips, overflow, scroll, fractional DPI.
- Не обещать 120 FPS, пока реальное окно и нужные стресс-сцены не укладываются
  в бюджет 8.33 ms с запасом; для 60 FPS бюджет 16.67 ms.
