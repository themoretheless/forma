# Оптимизация по этапам — 6 сентября 2026

Каждый этап завершается отдельной серией: 3 процесса × 120 кадров после
20 кадров прогрева. Сцены, размеры, DPI и SHA-256 исходников одинаковые;
`scripts/compare-bench.mjs` отклоняет несовместимые серии. Apple M5, 24 GiB.
Частота кадров ниже — offscreen serialized throughput, не FPS экрана.
Фоновая нагрузка и частоты GPU не зафиксированы, поэтому небольшие различия
времени не считаются доказанным ускорением. См. [методику](BENCHMARKS.md).

## 1. Плоские тайлы и переиспользование буферов

Семантика `clip` на этом этапе не менялась: побайтовое сравнение со старым
binner подтверждает тот же порядок команд. `TileScratch` хранит плоский массив;
native и WebGPU переиспользуют GPU-буферы и bind groups до роста ёмкости.
Ключ сетки — число тайлов, а не каждый отдельный пиксель ширины/высоты.

Resize около 4K:

| Метрика | Baseline | Этап 1 |
|---|---:|---:|
| Rust alloc + realloc / кадр | 8 475.67 | 54.67 |
| Новые наши GPU-буферы / 120 кадров | 120 | 0 |
| Загрузки tile-индекса / 120 кадров | 120 | 40 |
| CPU подготовка/submit, среднее | 0.88 ms | 0.28 ms |
| Completed p95 | 12.21 ms | 10.71 ms |
| Offscreen кадры/с | 118.33 | 143.60 |

Число аллокаций снизилось на 99.35%; оно не стало нулём, поскольку счётчик
охватывает также wgpu и создание тестового target. Ёмкость резервируется с запасом:
на этом этапе GPU-буферы 4K-кнопки выросли примерно с 210 до 280 KiB. Это осознанный
обмен небольшой памяти на отсутствие перевыделений, а не уменьшение каждой метрики.
GPU shader ещё прежний, поэтому вариации его времени не приписываются этапу 1.

Артефакты: `.forma/perf/step1-retained-2026-09-06/COMPARISON.md` и `results.json`.
Эталонные GPU-пиксели для следующего этапа: `.forma/perf/step1-goldens/`.

## 2. Отсечение невидимых команд и clip-групп

Команда попадает только в тайлы, пересекающие её видимую область и области
всех родительских clip. Парные push/pop включаются вместе только там, где есть
содержимое. Сохраняются порядок рисования, вложенность и запас для AA до
пересечения границ, включая дробный DPI. Шейдер не менялся.

Все **54 GPU-изображения побайтно совпали** с эталонами этапа 1: исходная сцена,
вложенные полупрозрачные/прокручиваемые группы, скругления, DPI 1/1.25/2.
Добавлены CPU-регрессии для пустых групп и пересекающихся AA-краёв.

Первая полная серия (`step2-clip-culling-2026-09-06`) показала ускорение текста,
но сильную просадку простой кнопки. Мы не приняли это как результат без проверки:
в измеряемой анимации binner вообще не вызывался, а времена одной версии сильно
различались между процессами. Выполнена дополнительная серия из 48 процессов:
4 соседние пары A/B на сценарий, порядок AB/BA сбалансирован, по 240 кадров.
Ни сборки, ни другие бенчмарки параллельно не выполнялись.

| Сценарий | Глобальные clip: кадры/с | Отсечение: кадры/с | GPU pass mean, A → B |
|---|---:|---:|---:|
| Кнопка 800×400 | 607.2 | 611.0 | 0.69 → 0.39 ms |
| Кнопка 1920×1080 | 310.2 | 606.0 | 2.02 → 0.76 ms |
| Кнопка 3840×2160 | 230.5 | 334.2 | 4.64 → 1.40 ms |
| Resize около 4K | 135.3 | 203.5 | 3.90 → 1.59 ms¹ |
| 40 текстовых блоков | 71.2 | 191.8 | 11.72 → 4.84 ms |
| Текст + 12 вложенных clip | 29.7 | 123.1 | 31.67 → 6.93 ms |

¹ Только отдельный статический pass конечного размера, не стоимость resize.
Это медианы процессов. В контрольных парах простой кнопки throughput менялся
от −1.6% до +1.6%: первоначальная сильная регрессия **не воспроизвелась**.
Нагрузка ОС и частоты GPU по-прежнему не контролируются; точные коэффициенты
не гарантируются для приложения. Рост CPU % в быстром неограниченном цикле
не равен росту CPU-стоимости одного кадра.
При этом измеренное CPU submit wall-time тоже выросло: текст 0.185 → 0.383 ms,
вложенные clip 0.126 → 0.388 ms. Поэтому этот этап не объявляется ускорением
CPU во всех сценариях; его основной подтверждённый результат — меньше GPU-работы
и памяти. В steady-кадрах обе версии уже не вызывают binner.

Контрольный executable A воспроизводит tile-содержимое этапа 1, но перед ним
также вычисляет и отбрасывает новые ranges. Поэтому его CPU-время binner при
resize не является точным повторением этапа 1. Для steady animation/forced это
не влияет: обе версии строят тайлы только до измеряемой фазы. Детали, SHA-256
обоих executable, raw results и диапазоны повторений:
`.forma/perf/clip-ab-2026-09-06/REFERENCE.md` и `paired/REPORT.md`.

Независимо от временного шума, ёмкость наших GPU-буферов уменьшилась:
у 4K-кнопки 286 768 → 155 696 байт (−45.7%), текст 1080p
1 638 448 → 655 408 байт (−60%). Это не общая VRAM; target остаётся прежним.

## 3. Общая неизменяемая геометрия

`CachedList` и native `Renderer` разделяют `Arc<DisplayList>`.
Покадровое сравнение всех `commands`/`edges` заменено на O(1) `Arc::ptr_eq`;
вторые копии массивов больше не нужны. Renderer удерживает strong reference,
поэтому повторное использование адреса нового объекта не даёт ложного cache hit.
Существующий Rust API `vector_list() -> Ref<DisplayList>` сохранён.

Hover/focus/tick и изменение размера viewport не меняют snapshot. DPI, фон,
прокрутка и успешная загрузка исходников/компонента создают новый snapshot.
Ошибка парсинга сохраняет предыдущий. Повторная загрузка даже идентичного
исходника теперь вызывает одну загрузку геометрии: это осознанный компромисс
вместо постоянного сравнения массивов. Новые geometry-setter должны инвалидировать
кэш, а не менять опубликованный snapshot.

Отдельная полная серия: `.forma/perf/step3-shared-geometry-2026-09-06/`.
Медианы памяти, до → после:

| Сцена | Дублированные массивы renderer, байт | Живые Rust-байты после серии | RSS после серии |
|---|---:|---:|---:|
| Кнопка 800×400 | 17 424 → 0 | 314 951 → 297 597 | 18.91 → 18.81 MiB |
| 40 текстовых блоков | 444 032 → 0 | 1 400 421 → 956 459 | 19.86 → 19.44 MiB |
| Текст + вложенные clip | 445 952 → 0 | 1 565 246 → 1 119 364 | 20.11 → 19.52 MiB |

`cpu_geometry_cache_bytes=0` означает отсутствие **дублированных массивов**,
а не отсутствие геометрии в RAM. `cpu_shared_geometry_bytes` показывает ёмкость
общих commands/edges (без Arc/Vec headers); её надо считать один раз вместе
с моделью. В этих сценах 24 576 / 630 784 / 630 784 байт соответственно.
Rust live bytes не равны RSS, а RSS не равен VRAM.

При анимации geometry uploads = 0 во всех повторениях. Аллокации steady-кадра
остались 43.25, resize — 54.67: они включают wgpu и не устранялись этим этапом.
Рост живых Rust-байтов за измеряемую GPU-фазу не наблюдался. GPU-буферы и target
не изменились. Шейдер и содержимое тайлов прежние, поэтому изменения GPU time
в отдельных сериях не приписываются замене cache identity.

Первая полная серия снова дала разнонаправленные времена: текст 183 → 164,
вложенные clip 76 → 51 offscreen кадров/с; даже неизменённый CPU fallback замедлился.
Она сохранена без выборочного удаления результатов. Для проверки выполнена
контрольная A/B-серия тем же `interleave-bench.mjs`; её результаты — в
`step3-shared-geometry-2026-09-06/paired/REPORT.md`.

В контрольной серии этап 2 → этап 3:

| Метрика | Этап 2 | Этап 3 | Медиана попарного изменения |
|---|---:|---:|---:|
| Текст: CPU submit mean | 0.280 ms | 0.190 ms | −36.6% |
| Вложенные clip: CPU submit mean | 0.326 ms | 0.203 ms | −24.7% |
| Текст: offscreen кадры/с | 104.0 | 105.5 | +0.4% |
| Вложенные clip: offscreen кадры/с | 43.6 | 46.4 | +0.5% |
| Кнопка 4K: offscreen кадры/с | 254.1 | 173.5 | −20.1% |

Точечные значения — медианы процессов; последний столбец — медиана попарных
отношений, не отношение двух медиан. У 4K-кнопки попарный throughput-разброс
−38.4…+18.7%; у текста CPU submit −67.1…+110.7%. Поэтому устойчивый прирост
FPS этапа 3 **не подтверждён**, как и отсутствие регрессий скорости на всех
сценариях. Экономия памяти и исключение O(n)-сравнения подтверждены отдельно;
для точного вывода о latency нужна спокойная машина/контролируемая нагрузка.
Все исходные и контрольные серии сохранены вместе с наблюдаемым разбросом.

## Проверки и состояние сборки

- 66 Rust-тестов прошли; отдельный hardware-тест на Metal тоже прошёл.
- 69 JS-тестов прошли, включая повторную попытку WebGPU после ошибки загрузки
  буфера/bind group и корректность попарного benchmark-отчёта.
- После этапа 3 все 54 GPU-изображения снова побайтно совпали с эталонами этапа 1.
- Release native и WASM собраны, production build Studio проходит.
- Открытый Studio перезагружен без изменения файлов виртуального проекта.
  MCP подтвердил `rust-wasm-webgpu`, `gpuFallbackReason=null`, ошибок разметки нет.
- Native window FPS остаётся недоступным в этой сессии; offscreen не подменяет его.

CPU raster-cache cleanup, локальная геометрия scroll/glyph cache и небольшие
покадровые аллокации — следующие отдельные этапы; здесь они не объявляются готовыми.
Качество AA и синхронизация native resize не изменялись.

## Проверки изображения

`gpu_check` умеет записывать и сравнивать точные GPU-пиксели независимо от CPU AA:

```sh
FORMA_GPU_GOLDEN_DIR=.forma/perf/goldens/image FORMA_GPU_GOLDEN_MODE=record \
  cargo run --offline --manifest-path vector-ui/Cargo.toml --release --features gpu \
  --example gpu_check -- path/to/scene.ui path/to/Button.ui
# После оптимизации, без MODE=record:
FORMA_GPU_GOLDEN_DIR=.forma/perf/goldens/image \
  cargo run --offline --manifest-path vector-ui/Cargo.toml --release --features gpu \
  --example gpu_check -- path/to/scene.ui path/to/Button.ui
```

Запись отказывается перезаписывать существующий эталон. Проверка требует полного
побайтового совпадения; число кадров и условия совпадают между запусками.
