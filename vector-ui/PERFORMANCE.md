# Производительность рендера

Добавлен отдельный векторный GPU-путь для native/WebGPU: см. [GPU.md](GPU.md).
Ниже описаны CPU-оптимизации и CPU fallback; они не означают, что GPU-путь
сначала рисует кадр на CPU.

## Изменено

- Studio запускает нативное приложение через `cargo run --release --offline`.
- Один кэш на экземпляр: геометрические маски, готовый слой текста/SVG/clip,
  последний кадр. Новый размер растеризуемой сцены/DPI/scroll или новый экземпляр
  инвалидирует кэш. Размер нативного окна отделён от размера этой сцены.
- Цвета анимации меняют только композицию кадра. 4 исходных образца покрытия
  фигуры и 16 образцов clip сохранены; пересчёт геометрии убран из анимации.
- Внутри и за пределами прямоугольников нет повторного дорогого расчёта
  скруглений; расчёт фигуры ограничен её bounding box при построении кэша.
- При неизменном визуальном состоянии pointermove не запрашивает перерисовку.
  Это действует в native и WASM-preview. Размер framebuffer учитывается отдельно.
- Нативный цикл ждёт события; redraw-цепочка работает только во время анимации.
  Движение мыши больше не сбрасывает часы анимации; surface не resize-ится каждый кадр.
- MCP `vector_status.rasterStats`: `[geometryBuilds, paints]`, чтобы видеть
  реальное использование кэша. Счётчики сбрасываются вместе с экземпляром.

## Воспроизводимый замер

```sh
cargo run --offline --manifest-path vector-ui/Cargo.toml --release --example raster_bench
```

Можно добавить два аргумента: пути к скомпилированным scene.ui и Button.ui,
полученным от Studio. Замер без окна: включает растеризацию и копию возвращаемого
RGBA, но не включает загрузку в canvas/softbuffer, композитор ОС или компиляцию.
Пять кадров на группу; цифры ориентировочные, не percentile-статистика.

Замер на этой машине, встроенный пример одной кнопки:

| Framebuffer | До, debug, анимация | До, release, анимация | После, release, анимация | После, первый кадр |
|---|---:|---:|---:|---:|
| 400×200 | 64.6 мс | 2.35 мс | 0.26–0.33 мс | 1.8–2.5 мс |
| 800×400 | 253.8 мс | 9.23 мс | 1.28–1.44 мс | 6.5–6.6 мс |
| 1600×1000 | 1855 мс | 56.9 мс | 5.17–5.51 мс | 23.2–23.5 мс |

Повторный неизменный кадр 800×400: 0.06–0.14 мс (копия кэша).
В обычном покое этот вызов вообще не нужен. Замеры зависимы от нагрузки;
они не гарантируют FPS приложения и не заменяют профилирование больших сцен.

Старый рендер оставлен только под `cfg(test)` как эталон. Pixel-regression
проверяет прозрачность, дробный DPI, текст, обрезку, прокрутку и переходы:
допуск 2/255 в premultiplied-каналах из-за изменения порядка округления композиции.

## Resize нативного окна

Причина замедления: ключ кэша включал физический размер окна. При растягивании
на каждый новый размер заново выделялись все маски и RGBA-слои, пересчитывались
скругления/текст и смешивались миллионы пустых пикселей. Затем полный RGBA-кадр
копировался и преобразовывался в XRGB для softbuffer.

Теперь `Button::paint_native` сохраняет кэш по границам фиксированной сцены
(включая видимое переполнение примитивов), а не по размеру окна. Готовый XRGB
также кэшируется. Resize только копирует видимые строки в буфер ОС и заполняет
пустое место. Уменьшение окна не уничтожает кэш. DPI, scroll, новые исходники и
цвета по-прежнему инвалидируют соответствующий слой. AA не упрощается, кадр не
масштабируется. Для окна больше 4096 px не применяется ограничение размера
маленькой растеризуемой сцены.

```sh
cargo run --offline --manifest-path vector-ui/Cargo.toml --release --example resize_bench
```

Встроенная кнопка 400×200, DPI 2, 20 изменений физических размеров окна:

| Начальный framebuffer | Старый путь, среднее | Новый путь, среднее | Новый путь, первый кадр |
|---|---:|---:|---:|
| 1600×1000 | 21.24 мс | 0.13 мс | 5.33 мс |
| 3200×2000 | 83.12 мс | 0.59 мс | 5.80 мс |
| 3840×2160 | 107.28 мс | 0.58 мс | 6.19 мс |

Среднее — по 19 кадрам после первого. Перестроения растеризации: **20 → 1**.
Замер включает заполнение host-буфера, но **не** выделение буфера ОС,
`surface.resize`, `present` и работу композитора; это не полный frame time.
Оба пути измеряются в одной release-сборке. Это ускорение фиксированной сцены
в большом окне, не замер адаптивного layout или большого дерева контролов.

Пять регрессионных тестов `tests/native_resize.rs` проверяют точное совпадение
пикселей со старым RGBA→XRGB путём, переполнение, вложенный clip, дробный DPI,
анимацию, scroll, замену разметки и большое окно 5000×1800. Лимит CPU-сцены
4096 px по оси / 8 388 608 пикселей остаётся: огромные реальные сцены требуют
тайлов или GPU. Превышение бюджета теперь даёт явную ошибку, а не пустой кадр.

## Следующее развитие архитектуры (ещё не реализовано)

1. Постоянное дерево UI и раздельные признаки изменения: layout, paint,
   composition. Изменение цвета не должно пересоздавать компонент или layout.
2. Независимый от backend список рисования с bounds, transform, clip-id и
   resource-id. Один и тот же список для CPU, GPU и диагностики Studio.
3. Кэш по элементам/тайлам и dirty rectangles. Сейчас кэш целой растеризуемой
   сцены: scroll перестраивает его, а анимация смешивает всю эту область.
   Вложенные clip временно выделяют полные слои — их нужно ограничить bounds.
4. Общий glyph atlas/кэш SVG и лимит памяти в байтах с LRU-вытеснением.
   Сейчас кэш слоёв принадлежит экземпляру и ограничен одним viewport, но не
   глобальным бюджетом памяти. Большие сцены/глубокие clip всё ещё дороги.
5. Расширение первого GPU-backend через wgpu; CPU остаётся fallback и эталоном.
   wgpu — доступ к GPU, а геометрия, стили и контролы остаются нашими:
   https://docs.rs/wgpu/latest/wgpu/

Порядок: дерево/инвалидация → список рисования → локальные кэши → GPU.
Перенос нынешнего полного пересчёта на GPU сам по себе не исправит архитектуру.
