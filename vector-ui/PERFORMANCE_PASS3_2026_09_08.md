# Третий проход: scroll без пересборки геометрии, 8 сентября 2026

Baseline: `9b846c9`, содержащий первые два прохода. Apple M5, 24 GiB, release,
default features, отдельные Cargo target dirs для двух версий. Сырые результаты,
порядок прогонов и описание: `.forma/perf/scroll-uniform-2026-09-08/`.

## Что изменилось

Раньше `Runtime::scroll` и `Button::scroll` инвалидировали DisplayList.
Следующий кадр заново обводил все glyph-контуры, собирал commands/edges,
загружал их в GPU и перебинивал тайлы. Для списка из 64 текстовых контролов
это стоило около 1,7 мс и 1431 аллокацию на каждый шаг колеса.

Теперь геометрия строится один раз в координатах содержимого, без смещения.
Пятый vec4 команды, ранее зарезервированный, хранит режим scroll:

| `commands[16]` | Значение | Как рисуется |
|---|---|---|
| 0 | fixed | Frame, фон, viewport-clip: без изменений |
| 1 | content | `bounds - scroll`; для glyph/shape edges пиксель сдвигается на `+scroll` |
| 2 | vertical thumb | `bounds.y + scroll.y * commands[17]` |
| 3 | horizontal thumb | `bounds.x + scroll.x * commands[17]` |

Смещение приходит в uniform `Params.scroll` (uniform вырос с 48 до 64 байт),
одинаково в native wgpu и WebGPU. CPU-биннер тайлов применяет те же формулы
через `scrolled_bounds`, поэтому scroll обновляет только индекс тайлов и
16 float параметров. `Arc<DisplayList>` сохраняет identity: у native это
`Arc::ptr_eq`, у WebGPU `geometry_revision`. `layout_revision` по-прежнему
меняется при scroll, теперь он означает «перебинить тайлы и обновить uniform».

CPU-растеризация не использует DisplayList и не менялась: pixel hashes CPU
на DPI 1 / 1,25 / 2 совпали до и после.

## Библиотека: стоимость одного шага scroll

Медианы трёх тихих процессов на версию; 100 операций на строку. Сцена:
Frame 320×160 со Scroll, контролы 640×45 с одной текстовой меткой, DPI 1,25.
`runtime_scroll` включает scroll и получение snapshot; `runtime_scroll_tiles`
дополнительно строит индекс тайлов для 400×200 через WASM-совместимый
`gpu_tiles` (он возвращает новый Vec, отсюда 8–13 аллокаций; native renderer
использует retained scratch и не аллоцирует).

| Сценарий | До | После |
|---|---:|---:|
| Scroll, 1 контрол | 25,9 мкс, 22 alloc | 0,061 мкс, 0 alloc |
| Scroll, 16 контролов | 418 мкс, 371 alloc | 0,39 мкс, 0 alloc |
| Scroll, 64 контрола | 1 704 мкс, 1 431 alloc | 1,43 мкс, 0 alloc |
| Scroll + тайлы, 1 контрол | 27,1 мкс, 30 alloc | 1,6 мкс, 8 alloc |
| Scroll + тайлы, 16 контролов | 422 мкс, 382 alloc | 5,3 мкс, 11 alloc |
| Scroll + тайлы, 64 контрола | 1 698 мкс, 1 444 alloc | 14,6 мкс, 13 alloc |
| Трафик allocator, scroll 64 контрола | 5 141 008 байт | 0 байт |
| Один Button со Scroll, 64 метки | 1 522 мкс | 0,07 мкс |

Строки «до/после тайлов» для baseline взяты из одного тихого процесса
(`base4`), остальные из трёх. Хеши индексов тайлов совпали между версиями на
всех трёх сценах: новый биннер со смещением даёт тот же результат, что старый
на пересобранной геометрии.

Не заявляется: ускорение первого кадра, DPI-перестроения, прогретого snapshot
без scroll и GPU-времени кадра. Glyph cache между разными текстами не
добавлялся; изменение текста по-прежнему перестраивает контуры.

## Проверки

- 111 обычных Rust-тестов, 14 тестов display_list (два новых: identity при
  scroll, режимы content/thumb и биннер со смещением) и остальные интеграционные
  прошли с `--features gpu`.
- Аппаратные Metal-тесты (`--ignored`): 2 прошли, включая smoke-тест, который
  теперь требует 0 загрузок геометрии и ровно одну загрузку тайлов на scroll.
- `gpu_check` на Metal: все сцены прошли; на сцене `nested-scroll` со
  смещением (10, 4) метрики расхождения GPU/CPU до и после совпали побайтно
  (mean 0,0213/255, max 23, 44 канала > 4 при 400×200; аналогично на остальных
  пяти размерах). Это сравнение с CPU-эталоном, не GPU golden-набор;
  goldens прошлых этапов в этом worktree отсутствуют.
- Свежий WASM собран, JS: 240 тестов прошли, 1 упал (`versions.test.js`,
  спавн в системном tmp). Тот же тест падает на неизменённом главном checkout,
  к правкам он не относится. Production Studio собрана.
- Studio через WebGPU: scroll больше не вызывает `gpu_commands`/`gpu_edges`,
  только `gpu_tiles` и `gpu_params`; проверено unit-тестами painter, в
  браузере вручную не проверялось.

## Ограничения

- Позиции thumb и edge-сдвиг вычисляются в шейдере другим порядком f32-операций,
  чем раньше в CPU-сборке команд. При scroll = 0 результат идентичен;
  при ненулевом scroll возможны различия в младшем бите AA-покрытия. На
  `gpu_check` этого не видно, но побайтовые GPU golden при ненулевом scroll
  потребуют перезаписи.
- Reveal-эффект хранит центр в экранных координатах в paints, а bounds в
  координатах содержимого; в шейдере bounds сдвигаются, как раньше.
- Scroll внутри вложенных Scroll не поддерживается, как и до изменения.

```sh
cargo run --offline --release --manifest-path vector-ui/Cargo.toml --example text_perf
cargo run --offline --release --manifest-path vector-ui/Cargo.toml --features gpu --example gpu_check
cargo test --offline --release --manifest-path vector-ui/Cargo.toml --features gpu -- --ignored
```

# Часть 2: аналитическое покрытие текста на GPU, 8 сентября 2026

Шейдер считал покрытие glyph-путей и `ContentShape` четырьмя точечными
пробами на пиксель, в каждой пробе обходя все рёбра пути. Теперь для каждого
ребра, обрезанного строкой пикселя, берётся точный интеграл
clamp(x(y) - px, 0, 1) dy со знаком направления; сумма по рёбрам даёт площадь
с учётом winding, coverage = min(|sum|, 1). Один проход по рёбрам вместо
четырёх и непрерывное сглаживание без ступеней 25%. Заодно убрано копирование
структуры Command на каждую команду в каждом пикселе, которое появилось в
первой части: смещение scroll применяется только к bounds как vec4.

## Парные A/B, native wgpu/Metal

`scripts/interleave-bench.mjs`: 4 соседние пары AB/BA на сцену, 240 кадров
после 20 прогрева, DPI 2, одинаковые fixtures (`.forma/perf/fixtures-2026-09-08`).
Три эксперимента, все сохранены в `.forma/perf/ab-*-2026-09-08/`:

| Эксперимент | Текст 1080p: кадры/с | Текст: GPU pass | Nested clip: кадры/с | Nested: GPU pass |
|---|---:|---:|---:|---:|
| HEAD → scroll как uniform (часть 1, с копией Command) | 190 → 172; −9,8% | 4,97 → 6,20 мс; +26,5% | 118 → 113; −3,7% | 6,76 → 7,20 мс; +7,8% |
| Часть 1 → + аналитический текст | 207 → 282; +40,9% | 3,72 → 2,59 мс; −30,2% | 122 → 134; +11,6% | 6,72 → 5,49 мс; −18,9% |
| HEAD → финал (обе части, без копии Command) | 170 → 216; +32,7% | 6,39 → 4,11 мс; −35,6% | 124 → 140; +11,6% | 6,27 → 5,54 мс; −11,0% |

Ячейки: медианы четырёх процессов и медиана попарных изменений. В финальном
эксперименте попарные изменения текста: throughput +0,7…+62,3% (все четыре
положительные), GPU pass −67…−2,2% (все отрицательные); nested: +5,8…+14,8%
и −18…−5,2%. Простые сцены ImageButton: throughput −8,3…+60,4%, GPU pass
в основном ниже, устойчивой регрессии нет.

Первый эксперимент показал замедление текста после части 1. Диапазоны
пересекались (GPU pass текста в парах −4,9…+139%), но копирование
Command в `scrolled()` было реальной лишней работой и удалено; отдельно его
вклад не измерялся, третий эксперимент сравнивает HEAD с финалом целиком.
Машина не изолирована; CPU submit и CPU % в этих сериях шумят сильнее, чем
GPU pass, и как результат не используются.

## Проверки

- `tests/runtime_gpu.rs`: новый аппаратный тест сравнивает GPU-текст и
  `ContentShape` с независимым scanline-эталоном (64 подстроки, точные длины
  перекрытия по X, nonzero winding, последовательная композиция). DPI 1 / 1,25 / 2:
  mean 0,0027 / 0,0024 / 0,0013 на 255, max 2/255, ни одного канала > 4/255.
  Первый вариант эталона с 8×8 точечными пробами давал до 14/255 на
  горизонтальных штрихах: это была квантизация эталона, не шейдера.
- `gpu_check`: все сцены прошли. Пока CPU-эталон считал текст 2×2 пробами,
  число каналов с расхождением > 4/255 на текстовых кромках выросло
  (input 400×200: 296 → 2461); после части 3 CPU считает ту же площадь и
  числа вернулись к исходным (296), порог 2% сохранён.
- Аппаратные Metal-тесты: 2 прошли. Обычные Rust-тесты (111 + интеграционные)
  прошли; JS 240 прошли, тот же не связанный `versions.test.js` падает;
  production Studio собрана. Шейдер в Studio импортируется из исходника,
  пересборка WASM для этой части не требуется.

## Ограничения

- Самопересекающиеся even-odd `ContentShape` считались бы иначе, чем раньше:
  формула насыщает |winding| ≥ 1. Forma такие фигуры не генерирует.
- Стоимость по-прежнему O(рёбра пути) на пиксель внутри bbox глифа; atlas
  покрытия не делался.

# Часть 3: CPU-растеризатор на той же точной площади, 9 сентября 2026

`text.rs::rasterize` и `shape.rs` считали 2×2 пробы; теперь они используют
ту же формулу, что шейдер: колонки целиком слева от ребра получают высоту
строки через разностный массив, колонки под ребром считаются замкнутой формой
`edge_area`, coverage = min(|sum|, 1) под правилом nonzero. Дробный clip
масштабирует граничные колонки/строки. Scratch по-прежнему одна строка.
Полигоны `ContentShape` идут через тот же растеризатор; для простых
многоугольников nonzero совпадает с прежним even-odd.

Результат: CPU fallback и GPU совпадают на кромках текста с точностью
округления; `gpu_check` вернулся к прежним числам (input 400×200: 296 каналов
с расхождением > 4/255), порог снова 2%. Unit-тест в `text.rs` проверяет
текст на трёх DPI и вогнутый полигон против scanline-эталона: максимум 2/255.
CPU pixel hashes всех текстовых сцен изменились, что ожидаемо.

CPU-стоимость по `raster_bench` (одна кнопка с текстом, DPI 2, по два
прогона каждой версии, не парная серия):

| Framebuffer | Cold, до → после | Animation, до → после |
|---|---:|---:|
| 400×200 | 1,79 → 1,98…2,11 мс | 0,31 → 0,29…0,30 мс |
| 800×400 | 7,04 → 6,18…6,97 мс | 1,06 → 0,92…1,25 мс |
| 1600×1000 | 25,1 → 23,1…24,6 мс | 4,94 → 5,34…5,86 мс |

Различия в пределах разброса между прогонами; ускорение или замедление CPU
не заявляется. Warm-кадр (копия кэша) не изменился: 0,010 / 0,038 / 0,20 мс.
