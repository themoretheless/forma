# Studio: оптимизация оболочки — 8 сентября 2026

Этот проход относится к браузерной оболочке Studio. Rust raster/GPU алгоритмы
не менялись; прежние native-замеры не выдаются за результаты новой версии.

## Исправлено

- **Передача кадров:** кнопки, дерево, меню и статус получают вложенный canvas.
  PNG/base64 и запись CSS image убраны из их анимации. `input` и `select`
  сохраняют CSS fallback: они не могут содержать canvas. У fallback один общий
  scratch canvas. Размер backing store меняется только при изменении размеров.
- **Аллокации в JS:** описание DOM и JSON-сигнатура пересчитываются только
  после изменения содержимого, состояния или размеров. Кадры Reveal используют
  сохранённый spec. Очереди кадров чередуют два Set. Библиотека файлов,
  параметры метрик и MediaQueryList создаются один раз на mount.
- **Изменения DOM:** вместо полного поиска по Studio обрабатываются добавленные
  поддеревья. Изменения внутри CodeMirror, предпросмотра и собственных canvas
  не запускают поиск контролов. Отсоединённые записи удаляются.
- **Память:** невидимый контрол освобождает Runtime и обнуляет backing store.
  При destroy удаляется canvas; освобождается общий scratch. Повторная установка
  `textContent` хостом не теряет canvas: поверхность повторно присоединяется.
- **Время жизни:** canvas-tools и element-tools освобождают DOM/window listeners,
  ResizeObserver и захват указателя при HMR. Добавлен тест, что удалённая Studio
  больше не реагирует на команды редактирования.

## Архитектура / SOLID / DRY

`studio-shell-controls.js` описывает компонент, `studio-shell.js` связывает
состояние DOM с Runtime, `studio-shell-painter.js` отвечает только за передачу
пикселей и жизнь поверхности. Painter принимает document, что позволяет
проверять его без запуска всей Studio. Общий `event-scope.js` задаёт владельца
подписок и сохраняет capture/passive. Отдельные классы, контейнер DI и новый
универсальный UI framework для этого не вводились.

## Замер передачи готовых пикселей

Открыть `/bench/studio-shell.html` при работающем `npm run dev`.
Один и тот же набор 12 кадров получен через реальный Rust/WASM. Размер контрола
160×32, DPR 2, RGBA 320×64. Шесть чередующихся AB/BA выборок по 160 операций,
прогрев 24 операции. Измеряется вызов передачи, а не растеризация или вывод
полного кадра на дисплей; браузер может объединять canvas-записи в композиции.

| Путь | Медиана, мс/передачу |
|---|---:|
| Прежний canvas → PNG/base64 → CSS | 1,4472 |
| Прямой canvas | 0,016875 |

Ускорение этого участка — около 85,8×. Это **не** ускорение всей Studio/FPS.
После 984 передач новый путь: 0 PNG, 1 resize, 81 920 учтённых RGBA-байт.
После dispose — 0. Счётчик учитывает размер backing store, не JS heap,
нативную память браузера, задержку GC или GPU-резидентность. Для всей Studio
снижение RSS/heap численно не измерялось.

## Ограничения и следующие измерения

- `Runtime.content_pixels` по-прежнему возвращает Vec/Uint8Array. Переход
  WASM → JS не стал zero-copy. Его стоит измерять отдельно прежде, чем менять
  API и вводить риск протухших views после роста WASM memory.
- Input/select всё ещё используют PNG при изменении изображения.
- Один canvas на видимый контрол увеличивает число DOM-узлов. Проверены
  команды и отрисовка в Studio; влияние на compositor нужно измерять отдельно
  на больших панелях. Пиксельные буферы вне видимой области освобождаются.
- Очистка подписок добавлена двум инструментам холста; это не аудит жизненного
  цикла всех модулей приложения.

Проверки: 248 JS-тестов, production build, браузерные действия панели и меню.
