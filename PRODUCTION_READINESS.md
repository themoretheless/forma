## Частичное обновление paint buffer

В native wgpu renderer вместо полной передачи массива цветов пишется один
непрерывный диапазон от первого до последнего изменённого f32. Выравнивание
4 байта; при изменении длины/перевыделении буфера передаётся весь payload.
Определение диапазона не создаёт коллекций; сравниваются биты (включая -0/NaN).
Unit-тест проверяет восстановление, resize, разделённые изменения и особые биты.

Metal integration test с чтением пикселей: локальный hover отправляет 12 вместо
64 байт при DPI 1 / 1,25 / 2. Соседний контрол побайтно неизменен, повторных
загрузок геометрии нет. Большие сцены и парные замеры времени ещё необходимы;
ускорение FPS/времени кадра на основании этих байтов не заявляется.

## WebGPU paint transport

Браузерный storage pool поддерживает частичную запись paint payload с
выравниванием на 4 байта. Неизменившиеся байты не отправляются. При смене сцены,
изменении длины или после неудачной записи выполняется полная запись.
CPU snapshot копируется в переиспользуемый Uint8Array: одна дополнительная
копия paint payload на активный painter, освобождаемая вместе с pool.
Geometry/tiles не получают дополнительные CPU snapshots.
14 целевых JS-тестов прошли, включая восстановление после частичного отказа.
Это проверки API с mock GPU device; аппаратный браузерный WebGPU-тест и
измерения на больших сценах пока остаются открытыми.

## Ограничение загрузки результатов design.*

Результаты ранее загружались через Promise.all(readFile) без ограничения размера.
Теперь readDesignValues читает последовательно в один scratch 1 МиБ + 1 байт,
проверяя суммарный объём до превращения очередного результата в строку.
Общий лимит — 1 МиБ UTF-8; при превышении возвращается ошибка, finally runner
удаляет временный каталог. Чтение не полагается на предварительный stat.size:
рост файла также ограничен числом прочитанных байт. Тесты проверяют ровно лимит,
превышение одним файлом и превышение суммой файлов; тест с rustc также прошёл.
Это ограничивает память Node при чтении результатов, но не память/диск самого
исполняемого Rust-кода. Изоляция исполнения остаётся отдельным открытым пунктом.

## Загрузка шаблонов в Rust-раннере: меньше аллокаций на каждый примитив

Причина искать дальше после квантования: разбор шаблонов — 93 % времени
load_component. Проба на 256 контролах с 65 ContentShape (нативный Cargo,
подсчёт аллокаций через thread-local GlobalAlloc, тесты по одному потоку):
template::parse 18,16 мс / 332 033 аллокации из 356 175 в загрузке целиком,
то есть ~18,6 аллокации на ContentShape. Разбор числа не при чём: 133 120
координат проходят str::parse::<f32> за ~1 мс.

Убраны лишние владения токеном: ident() и text_value() переносили строку из
токена через clone, теперь перемещают (std::mem::take) и только потом idущ
вперёд; координаты polygon читаются одним проходом сразу в Vec<[f32;2]> вместо
промежуточного Vec<f32> и chunks_exact. Порядок и тексты диагностик сохранены,
включая «Invalid polygon points» для нечётного/пустого/слишком длинного списка.

Нативный A/B (тот же тест, чередование base/opt, по одному потоку):
аллокации загрузки 356 175 → 251 215 (−29,5 %), 18,6 → 12,0 на ContentShape;
Runtime::from_sources на фикстуре 12,08/12,11 → 11,07/11,13 мс (−8 %),
фаза template::parse 18,16 → 10,97 мс. В WASM эффект скромнее: load_component
19,70–19,94 → 18,56–19,12 мс (−4,5 %) при побайтово одинаковом шаблоне входа
(sha выхода совпадает во всех кругах), то есть местный allocатор в wasm
дешевле, и выигрыш в основном в числе аллокаций, а не в времени.
cargo test --release: 135 тестов прошли; npm test — 265 из 266 (падает только
version command, как на чистом HEAD).

Отклонено: собственный быстрый разбор десятичных чисел — на всём корпусе
координат он дал бит-в-бит те же f32, но std-парсер стоит ~1 мс из 12, так что
усложнение не нужно. Методический вывод: cargo-пробы нужно запускать с
--test-threads=1, иначе параллельные тесты внутри одного бинаря удваивают
временные метрики (первый прогон показал 14 → 23 мс на том же коде).

## JS-сериализация шаблонов: общие значения экземпляров копируются один раз

После квантования и ускорения Rust-разбора осталась самая большая фаза — JS-часть
компиляции. Таймеры внутри функций в Node (256 ImageButton, медиана): полная
компиляция 23,4–24,5 мс, из них instantiate 11,9 мс (из них expandChildren 10,5 мс),
createElementTree шаблонного дерева 6,8 мс, подсчёт UTF-8 длин для
FORMA-TEMPLATES-1 2,5 мс, flatten 1,7 мс. Внутри expand(): propertyOrigins 6,8 мс
и evaluateProperties 4,8 мс; в createElementTree structuredClone 5,7 мс и
рекурсивная заморозка 1,2 мс.

Причина одна: экземпляры одного компонента раскрывают одни и те же значения
определения, а код на каждом экземпляре заново считал ссылки выражений, заново
строил одноэлементный «единственный источник» и заново клонировал дерево.

* expressionReferences() кэширует результат по идентичности value (WeakMap),
  регулярное выражение вынесено, обход идёт по Object.keys без массива пар;
  пустой список ссылок — один замороженный массив на весь процесс.
* propertyOrigins() для значения без ссылок возвращает один снимок
  «[{source, label}]»: по source для примитивов и по паре (value, source) для
  объектов. Значения со ссылками и дедупликация JSON остаются прежним путём.
* createElementTree() копирует и замораживает одним проходом вместо
  structuredClone + повторного обхода; общие значения определений получают один
  копированный замороженный объект на всё дерево (WeakMap по исходному значению),
  порядок обхода и «предок раньше потомка» в массиве nodes сохранены.

Парный A/B в одном Node-процессе (чередование старого и нового модуля, 11 кругов):
медиана 28,08 → 21,15 мс (−26 %), 10 из 11 пар в пользу нового (один выброс —
сборщик). Отдельными процессами: 23,8 → 17,9 мс. Проверка эквивалентности:
source, template, visualNodes, instanceTree и templateTree совпали побайтово на
сценах в 1, 3 и 256 контролов, длина транспорта осталась 1 758 116 байт.

Новые тесты («reference collection walks nested values…», «a reference-free value
contributes only its own source…») падают на прежней реализации и проходят на
новой; npm test — 267 из 268 (падает только version command, как на чистом HEAD).

Отклонено без выигрыша: ранний выход evaluate() для примитивов (таймеры не
сдвинулись), замена Object.fromEntries на присваивание в expand() — ключ
«__proto__» из разметки превратился бы в запись в прототип.

GPU/paint путь замерен и горячим не оказался: за компиляцию Rust отдаёт в JS
1 527 200 байт commands (2,67 мс), 2 065 776 байт edges (0,2 мс), 18 696 байт
tiles и 8 192 байта paints — примерно 3 мс и 3,6 МБ на компиляцию, то есть ~7 %
против 18 мс load_component. Клон кэшированных векторов обязателен границей wasm
(JS нужен owned буфер), а zero-copy вид на память wasm опасен: queue.writeBuffer
держит ссылку на буфер, а рост памяти wasm отвязывает ArrayBuffer. Что реально
остаётся в этом пути — не квантование байтов, а сокращение самого транспорта
(общее тело шаблона вместо повтора на экземпляр) и переиспользование Runtime между
компиляциями, чтобы geometry_revision не сбрасывался на каждом нажатии.

## Латентность ввода в Studio: пересъёмка после квантования и JS-оптимизаций

Метод: тот же fixture на 256 ImageButton (транспорт 1 758 116 байт — совпал с
Node-замером), Chrome 156 в режиме headless=new с WebGPU на Metal-адаптере, Vite
dev, реальный путь Studio: набор в contenteditable редактора внутри строкового
литерала (разметка остаётся валидной) → debounce 250 мс → compile() →
vectorPreview.render. Полная компиляция взята из PerformanceObserver(«longtask»),
фазы — временными таймерами внутри src/components.js и src/vector-preview.js;
после замера оба файла восстановлены из снимков и побайтово совпадают с HEAD,
npm test — 267 из 268 (падает только version command, как на чистом HEAD).
Скрытая вкладка для этого замера не годится: таймеры сжимаются до 1 с, а
Raster-канвасы не получают размер.

Числа (2 разминочные и 10 измеренных пар «вставка → удаление», медиана):
редактирование → старт задачи компиляции 256 мс; полная компиляция в браузере
59–69 мс, медиана 63,5 мс против базовых 113–118 мс (−44 %). Внутри неё
compileComponents 31,8 мс, vectorPreview.render 30,2 мс, из них load_component
23,9 мс и растр ≈6,3 мс; остальное — parse входного файла, controlTree и DOM —
≈1,7 мс. Прогноз из прошлых секций (−15…−18 за квантование и загрузку, ещё ~−6 за
JS) подтверждён с запасом.

Важное расхождение с Node: при побайтово одинаковом шаблоне JS-компиляция в
браузере медленнее в 1,9 раза (31,8 против 17,1 мс), load_component — в 1,3 раза
(23,9 против 18,5 мс). Браузерные выводы нельзя пересчитывать из Node-замеров, и
наоборот; сравнивать варианты нужно в одном браузере и одном процессе.
(Позже этот вывод про 1,9 раза проверили на изолированной работе и он оказался
неверным: см. секцию «Потолок JS-фазы» ниже. На 31,8 мс повлияло окружение
приложения в момент замера, а не V8 браузера; load-часть — 23,9 против 18,5 мс —
подтвердилась.)

Синхронная блокировка на нажатие в этом прогоне 17–31 мс (медиана 26,3) — это НЕ
те же 3,2–4,4 мс из базового замера: проба считает «execCommand → следующий
макротаск» и включает обновление DOM CodeMirror, перекладку видимых строк и
пересчёт стилей, тогда как база меряла таймером только refreshControlTree.
Отдельный таймер на этом пути не снимался, потому что src/main.js несёт чужую
незакоммиченную работу.

Проверено заодно, что браузерная компиляция не платит за кэш: за один компайл
ровно один повторный разбор изменённого входного файла (parses=1), обращений к
кэшу связанных определений — 1 попадание, 0 промахов, 0 вытеснений при 6 записях
и 2 МБ. То есть 27–32 мс JS — это работа раскрытия, а не промахи кэша. Разница
между прогонами одного и того же кода в этом пути ±15 % (63,5 мс в одном
замере, 57 мс в другом), поэтому выводять из браузера в Node нельзя и сравнивать
нужно только чередованием вариантов в одном процессе.

Отклонено без выигрыша: подсчёт UTF-8 длин для рамки FORMA-TEMPLATES-1 арифметикой
по charCodeAt вместо TextEncoder.encode().length — 1,59 против 1,48 мс на 256
шаблонах, потому что транспорт после квантования оказался чистым ASCII
(1 758 116 символов = 1 758 116 байт) и штатный энкодер идёт по быстрой ветке.
Заменить подсчёт на длину строки нельзя: тексты и имена из разметки могут быть
кириллическими, и тогда рамка разъехалась бы по байтам.

Следующий рычаг не изменился: сокращать сам транспорт (общее тело шаблона вместо
повтора на экземпляр) и переиспользовать Runtime между компиляциями.

## Сколько именно повторяется в транспорте: разложение оставшихся 57–63 мс

Разбор структуры транспорта показал, что дублировать там почти нечего, кроме
буквального тела шаблона: 256 шаблонов ImageButton содержат по 291 токену и
отличаются друг от друга ровно одним токеном (`text: 'Item N';`), а все остальные
6,8 КБ байт на экземпляр совпадают побайтово; после маскировки чисел и
строковых литералов остаётся один-единственный «скелет». При этом точных
дубликатов шаблонов нет ни одного, поэтому дедупликация по идентичности строк
даёт 0 % сокращения — экономить можно только на общем теле с по-экземплярными
подстановками, то есть на смене контракта.

Node-разбиение компиляции (256 экземпляров, медиана из 7 отборов, таймеры внутри
временной копии модуля; файл удалён после прогона):
- всего 16,95 мс; из них `compileInstances` 10,10 мс, в том числе `instantiate`
  7,88 мс (30,8 мкс на экземпляр при 6 узлах дерева), flatten 1,29 мс,
  фильтрация props 0,35 мс, сборка строки шаблона 0,24 мс;
- вне `compileInstances`: `createElementTree` шаблонного дерева 1,84 мс, рамка
  FORMA-TEMPLATES-1 2,26 мс (из неё 1,48 мс — `TextEncoder.encode().length`);
- масштабирование линейно по числу экземпляров (1→0,42 мс, 32→2,92 мс, 256→16,95 мс).

Отклонено без реализации: мемоизация `evaluate()` для «постоянных» поддеревьев.
Подсчёт показал, что 51 % объектных вызовов (5 888 из 11 520 на компиляцию) —
значения определения без ссылочных выражений, то есть кандидаты. Но безопасен
только строгий критерий «в поддереве нет ключей expr/expression/interpolation»:
для `expr`-листав результат считает `evaluateExpression`, а он вызывает
`reference()` и для идентификатора, и для `true/false` — значит мемо обязано
перепроверять независимость от props/state/environment для каждого литерала.
Строгий критерий отсекает как раз те самые цвета и длительности из
по умолчанию, то есть почти всю выгоду; выигрыш в 2–4 мс из 57–63 мс не стоит
сомнительной детерминированности в ядре интерпретатора.

Практический вывод: оставшиеся горячие фазы — JS-раскрытие (7,9 мс Node / ~32 мс
в браузере) и разбор в Rust (23,9 мс) — линейны по «экземпляры × размер тела», и
оба сокращаются одним и тем же: общий тело шаблона + переопределения на экземпляр
(`FORMA-TEMPLATES-2` в runtime.rs и `form_document.rs`, пересборка WASM, проверка
эквивалентности по control_count и пикселям). В пределах действующего контракта
сжатать нечего: дедуп по идентичности даёт 0 %, а экономия на подсчёте байт
измерима и отвергнута выше.

## Разбор шаблонов в Rust: токены borrow-ятся из исходника

Мотивация: после квантования геометрии в замерах 23 сентября осталось две
линейные фазы — JS-раскрытие (7,9 мс Node) и разбор транспорта в Rust (23,9 мс
в браузере). Дедупликация транспорта внутри `FORMA-TEMPLATES-1` измерена и
отвергнута (0 %), поэтому единственная доступная мишень — сам разбор.

Инструмент. Новый нативный бенч `vector-ui/examples/template_load_perf.rs`
читает настоящий транспорт, который выдаёт Studio: `node
scripts/transport-fixture.mjs` (тот же fixture, что
`scripts/compiler-session-bench.mjs`) кладёт в `.forma/perf/template-load/`
сцены на 1, 32 и 256 экземпляров. Транспорт на 256 — 1 758 116 байт с sha256
`80e6217a…`, то есть байт-в-байт тот же вход, что в браузерном прогоне 23
сентября. Бенч печатает отдельно чистый `template::parse` и всю загрузку
`Runtime::from_sources`, плюс FNV-дайджест `DisplayList` (commands + edges) как
страх эквивалентности геометрии.

Было (Node 24, release, Apple M5, 256 экземпляров): разбор 43,3 мкс на шаблон,
загрузка 11,52–11,75 мс, 274 255 alloc+realloc, 12,08 МБ запрошено; на один
разбор приходилось 877 аллокаций. Разбор — около 96 % времени загрузки: `load`
и `parse` различались только обвязкой сцены.

Изменения в `vector-ui/src/template.rs`, контракт транспорта не тронут:
- литералы без escape-последовательностей собираются одним байтовым сканом и
  одним копированием среза, а не посимвольным `push` в растущий `String`;
- `ContentShape { points }` разбирается одним проходом: убран
  `split_whitespace().clone().count()`, ёмкость оценивается по числу разделителе
  байтов с потолком в 4096 пар, границы (`< 3` пар, `> 4096` пар, нечётное число
  чисел) проверяются по ходу тем же сообщением `Invalid polygon points`;
- `Kind::Ident`, `Kind::String`, `Kind::Hex` переехали на `Cow<'a, str>` поверх
  строки источника: токен идентификатора или цвета больше не аллоцируется, а
  длинный список точек не копируется вообще; `seen`-множество повторяющихся
  полей держит `Cow`, клон заимствованного значения не выделяет память.

Стало: 27,9 мкс на шаблон (−36 %), загрузка 6,93–7,46 мс (−38 %), 91 471
аллокация на загрузку (−67 %), 163 на разбор (−81 %), 9,44 МБ запрошено
(−22 %). Сдержанный минус: живых байтов после загрузки стало 4,36 МБ против
4,23 МБ — ёмкость вектора точек теперь оценивается сверху.

Парный A/B на настоящем WASM в Node (тот же вход, сборка туда-сюда, три
чередующихся круга, медиана из 7 отборов): `load_component` 18,68 / 19,10 /
19,20 мс против 13,12 / 13,18 / 13,35 мс — −31 %. JS-компиляция на обеих сборках
19,1–19,8 мс, то есть не изменилась.

Эквивалентность: дайджест `DisplayList` идентичен до и после на всех трёх
сценах (1: 1375888489770191918, 32: 4896571815845383841, 256:
2260981288911909770 — команды 381 820 и рёбра 477 136), `cargo test` — 136
тестов зелёные, включая добавленный `shape_points_boundaries_and_string_escapes`
(границы числа пар, нечётный набор, выход за диапазон, escape-литералы, кавычки
двумя способами); `npm test` — 267 из 268, падает единственный прежний
`versions.test.js`, который падает и на чистом HEAD.

Отвергнуто по измерению: таблица интернирования ключевых слов (84 строки,
`binary_search`) вместо заимствования. Аллокации она срезала сильнее (682 → 300
на разбор), но время разбора выросло с 31,0 до 37,5 мкс — семь сравнений строк
на токен дороже, чем один `malloc`; наивный `Cow<'static, str>` дал тот же
регресс, что подтвердил и A/B по загрузке (9,86 против 9,47 мс).

Осталось в разбор: 163 аллокации на экземпляр — примерно по вектору точек и по
`HashSet` на каждый из 65 примитивов и мелочь обвязки. Следующая экономия того
же класса, что и выше (несколько процентов), а не кратная: кратную даёт только
общее тело шаблона с по-экземплярными подстановками (`FORMA-TEMPLATES-2`),
то есть смена контракта.

Эффект в Studio (headless Chrome 156, тот же прогон «нажатие → Live preview
обновлён», longtask, 12 отборов): медиана 58 мс против 63,5 мс 23 сентября при
диапазоне 54–60 мс, то есть −8 %. Фазные таймеры в этой сборке не ставились
(они были временными), поэтому раскладка по `render`/`load_component` не
переснималась; направление и величина подтверждены парным Node-прогоном на
идентичном входе. После этого изменения самый большой остаток — снова
JS-сериализация (~32 мс), то есть `FORMA-TEMPLATES-2`.

## JS-компиляция после ускорения разбора: профиль и три правки

Профиль CPU компиляции сцены из 256 экземпляров `ImageButton` (Node 22, 6 с непрерывной
компиляции, `--cpu-prof`) до правок, 17,2 мс на компиляцию:

- `propertyOrigins` (`src/property-origins.js`) — 19,5 %, из них 54 % самой функции на
  строке дедупликации (654 мс из 1215);
- сборщик мусора — 14,2 %;
- `copy` (`src/element-tree.js`) — 10,9 %;
- `TextEncoder.encode` ради длины байт транспорта — 10,8 %;
- `structuredClone` — 6,9 %, почти целиком один вызов в `compile`.

Правки, все внутри действующего контракта `FORMA-TEMPLATES-1`:

1. `clone()` в `src/components.js` был `structuredClone`. Компиляция клонирует
   кешированный разбор документа и связанные определения на каждый проход, а это обычные
   объекты, массивы и скаляры. Рекурсивная копия с картой идентичности сохраняет общие
   подграфы общими — как это делал `structuredClone` — и уходит на `structuredClone`
   только для нестандартных прототипов. На реальном разборе сцены: 0,42 мс против
   1,06 мс на клон.
2. Длину UTF-8 для рамки транспорта шаблон экземпляра (~6,9 КБ) почти всегда можно взять
   из `text.length`: кодирование только ради подсчёта длины заново выделяло 1,7 МБ за
   компиляцию. Быстрый путь по ASCII оставлен для `templateByteLength`, многобайтовый
   текст идёт через `encode` (этот случай покрывает тест framing). По 256 шаблонам:
   0,42 мс против 1,51 мс.
3. Ключ дедупликации происхождения — текст JSON от origin'а; текст источника
   запоминается по объекту источника, потому что одни и те же источники повторяются для
   каждого экземпляра определения. Изолированный вклад скромный: −2,8 % (медиана
   14,29 → 13,89 мс на 256 экземплярах, три согласованные пары).

Итог парного A/B (`scripts/compiler-session-bench.mjs`, медиана из пяти выборок, три
повторности, только эти два файла менялись): 256 session 16,18 → 13,71 мс (−15 %),
256 one-shot 16,98 → 15,00 мс (−12 %), 64 session 3,73 → 3,41 мс, 1 session
0,22 → 0,17 мс.

В браузере тот же сценарий (256 экземпляров, замер «нажатие → длинная задача
компиляции») изменений не показывает: парные медианы 62,5 и 64,0 мс после правок
против 64,5 и 63,5 мс до них, то есть разнос сопоставим с шумом самой измерительной
сводки (±1,5 мс). Экономия в 2,5 мс на JS-компиляции тонет в 60-мс задаче, где
половина времени — разбор и растеризация.

Эквивалентность проверяет `scripts/compile-digest.mjs`: сравнивает все каналы вывода
(`source`, `template`, `visualNodes`, `instanceTree`, `templateTree`, `previewNodes`,
`previewControls`) и размер транспорта на 1/3/32/64/256 экземплярах. До и после правок
совпали полностью, сессионная компиляция равна «холодной». Тесты: 268 из 269 — падает
только `test/versions.test.js`, как и до правок. Новые случаи: ASCII-шаблон в смешанном
мультибайтовом транспорте и дедупликация источников по структуре, а не по идентичности.

Оставшийся профиль после правок: сборщик мусора 17,0 %, `copy` из `element-tree.js`
12,8 %, путь `propertyOrigins` ~20 %, `expand` 7,3 %. Крупнейший остаток — не JS: 256
шаблонов транспорта отличались друг от друга одним символом (общий префикс 6821 байт из
6868 на экземпляр), и Rust разбирает этот текст целиком для каждого экземпляра.
Сокращение требует смены контракта — общее тело определения плюс значения экземпляра, то
есть `FORMA-TEMPLATES-2` и пересборки WASM.

### Что из аллокаций в `element-tree` действительно сработало

Второй шаг по тому же профилю: `copy` в `src/element-tree.js` стала 12,8 %. Встроенный
счётчик показал, что карта идентичности `copies` не попадает ни разу — 0 попаданий из
98 714 вызовов, потому что узлы экземпляров делят значения определения, а они к
этому моменту уже отдельные объекты. При этом 531 структура из 8 670 повторялась по
содержимому, то есть хэш-консинг дал бы 93,9 % экономии аллокаций.

Попробовали и отвергли: ключ из содержимого приходится собирать на каждом узле, и
это дороже самой копии. Парной прогон на 256 экземплярах — 14,87/15,27/14,68 мс до
против 25,06/25,21/23,82 мс после, то есть **+68 %**. Откат.

### Интернирование происхождений: самый большой остаток JS-фазы

Профиль после этих двух правок (256 экземпляров, 15,6 мс на компиляцию): сборщик мусора

### Три отрицательных результата в JS-фазе, чтобы их не перемерять

Профиль после четырёх принятых правок (256 экземпляра, 12,5 мс на компиляцию): GC
16,3 %, `copy` в `element-tree.js` 12,0 %, `expand` 8,4 %, путь `propertyOrigins` 6,5 %,
`compileInstance` 4,5 %, `templateByteLength` вместе с regex 7,8 %, `copyData` 3,7 %.
По трём верхним кандидатам измерено и отвергнуто:

1. Отказ от копии связанного определения на hit (`links.get` в `src/components.js`:
   `clone(saved.linked)` → общая ссылка) плюс глубокая заморозка кэшированной записи.
   Тесты (269 из 270, падает только предсуществующий) не находят ни одной записи в
   замороженный объект, все семь каналов вывода совпадают, но выигрыша нет: 256 session
   11,57–12,17 мс до против 12,14–13,60 мс после; без заморозки — 11,66–13,29 мс. Один
   экземпляр выигрывает 0,19 → 0,11–0,12 мс, это меньше шума прогона. Причина: копия
   определения не была горячим местом, а без неё каждый экземпляр попадает в `clone(n)`
   уже развернутого визуала (`components.js:402`) — работа переезжает, а не исчезает.
   Копия на hit к тому же сознательное решение, зафиксированное в
   `vector-ui/CACHE_POLICY.md`: выдавать отдельную копию, чтобы мутация визуального
   snapshot вызывающим кодом не отравила следующие компиляции.
2. Альтернативы проверке ASCII для длины транспорта: `TextEncoder.encodeInto` в
   переиспользуемый буфер — 0,824 мс против 0,405 мс на текущий regex по 256 шаблонам;
   ручной скан `charCodeAt` — 1,057 мс. Существующий путь уже самый быстрый.
3. Переписанный сериализатор шаблона (`serializeNode`, `literal` для массивов и шапка
   `compileInstance`) без `Object.entries`/`filter`/`map`/`join`, на последовательном
   конкате: вывод байт-в-байт тот же, 12 тематических тестов зелёные, но 256 session
   11,35/11,37/11,58 мс до против 11,36/11,38/11,62 мс после, 64 — плоско.

Вывод: внутри действующего контракта `FORMA-TEMPLATES-1` JS-фаза уперлась в
неустранимое — 1,76 МБ строк транспорта и копирование дерева снимков. Крупнейший
остаток теперь нативный, и его потолок измерен, а не оценён (проба `clone_cached` и
`parse_repeat` в `vector-ui/examples/template_load_perf.rs`, нативный release, 256
контролов): разбор стоит 25,2 мкс на шаблон против 1,31 мкс на клон уже разобранного
`Template` — 6,45 мс из 6,95 мс загрузки, то есть 93 %. Одно нажатие меняет текст одного
шаблона из 256, поэтому кэш разбора по содержимому даёт 255 клонов плюс один разбор:
0,33 + 0,03 ≈ 0,36 мс вместо 6,95 мс (−95 %). Аллокаций на попадании 76 против 163 на
разборе и 91 471 на всю загрузку. Ограничения проекта для такого кэша: ключ обязан
сверять полный текст, а не только короткий хеш (`vector-ui/CACHE_POLICY.md`), кэш должен
жить вне `Runtime` (Studio пересоздаёт объект `Runtime` на каждое нажатие —
`src/vector-preview.js:400`), сохранное определение отдаётся копией, и он попадает в
известную дыру бюджетов: native-кэш не ограничен единым бюджетом сцены.

## Кэш разбора шаблонов по содержимому в Rust

Описанный выше кэш реализован: `template::parse_cached` в `vector-ui/src/template.rs` и
единственный вызов из `Button::from_scene` (`vector-ui/src/lib.rs:100`). Ключ — полный
текст шаблона плюс весь `ButtonSpec`: 64-битный свёрточный хеш текста выбирает только
корзину, попадание требует совпадения строк и всех полей спека, как того требует
`CACHE_POLICY.md`. Хранимая запись отдаётся клонированием, поэтому правка
`control.template.content` (`vector-ui/src/runtime.rs:282`) не отравляет следующий
запрос. Кэш thread-local и живёт дольше `Runtime`: Studio пересоздаёт объект раннера на
каждое нажатие. Бюджет — 1 024 записи или 16 MiB расчётного веса, вытеснение по
давности использования, слишком большая запись возвращается без сохранения. Ошибки
разбора не кэшируются.

(−75 %); попадание целиком (хеш, сверка ключа, клон) — 1,80 мкс против 25,2 мкс разбора
(−93 %); аллокаций на попадании 76 вместо 163 на разбор и 91 471 на всю загрузку → 64 847.

не изменились ни на одной сцене (1: 1375888489770191918, 32: 4896571815845383841,
256: 2260981288911909770).

6,93–7,46 → 7,91 мс, то есть +14 % на добавление записей. Выгодка описывает правку одного
контрола; правка общего (размер `Frame`, `components/Button.ui`, вставка или удаление

Нативный A/B на настоящем WASM в Node (сборки туда-сюда, чередование вариантов, сценарий

## Потолок JS-фазы: браузер не медленнее Node, а упираться осталось в debounce

Проверка утверждения из секции про латентность ввода («JS-компиляция в браузере
медленнее в 1,9 раза»). Меряли одну и ту же работу в двух хостах V8: общий раннер
`js-phase-run.mjs` (одинаковый текст сцены, одинаковые 4 разминочных и 11
измеренных прогонов, медиана, проверка детерминированности выхода), Node против
страницы Chrome Dev 156 через dev-сервер, один и тот же собранный wasm для
`text_metrics`. Транспорт на 256 контролах побайтово совпадает в обоих хостах —
1 758 116 байт.

Числа (медиана, мс; два чередующихся раунда; `.forma/verification/pipeline/2026-09-24-native-parse-cache/isolated-compile-ab.jsonl`):

| контролов | Node | браузер (чистая страница) |
| --- | --- | --- |
| 1 | 0,34 / 0,34 | 0,30 / 0,20 |
| 32 | 2,27 / 2,40 | 3,00 / 1,30 |
| 256 | 12,27 / 12,23 | 8,40 / 8,20 |

Ранние прогоны того же сценария дали Node 11,99–12,82 и браузер 8,5–9,0 мс, а в
уже загруженной странице Studio — 8,9 мс на 256 контролах. То есть браузерная
компиляция изолированной работы не медленнее, а примерно в 1,45 раза быстрее
Node-версии; вывод про 1,9× измерял приложение (параллельные наблюдатели,
CodeMirror, свой компайл и состояние Studio), а не компилятор. Практическое
следствие: сравнивать варианты по-прежнему нужно только чередованием в одном
хосте, но ссылаться на Node как на «быстрый эталон» нельзя.

Профиль реальных 10 нажатий в загруженном Studio (`cpu-probe.mjs` в том же
архиве, Chrome Profiler через CDP): цикл «нажатие → Live preview обновлён»
274–286 мс, из них 250 мс — debounce, то есть на CPU остаётся ~28 мс. Расклад
непустых сэмплов плоский: (idle) 90,1 %, (program) 1,5 %, дальше максимум по
0,6 % на функцию — `getUint8ArrayMemory0` (склейка wasm-bindgen), сборка
мусора 0,5 %, `forma::Button::cached` 0,5 %, `copy` element-tree.js:26 0,4 %,
`draw` control-tree.js:48 0,4 %, `tokenize` expressions.js:21 0,3 %,
`visit` cache-budget.js 0,2 %, `hypotf` в wasm 0,2 %, `setAttribute` 0,2 %,
`execCommand` 0,2 %, `advanceStack` (@lezer/lr) 0,2 %. Отдельно проверена и
отклонена гипотеза, что горяча посимвольная UTF-8-кодировка строк в
wasm-bindgen: транспорт фикстуры на 256 контролах чистый ASCII (1 837 177
символов, 0 не-ASCII), так что резервный путь для этой сцены не включается.

Вывод: в JS-компиляции не осталось горячего пути, который окупал бы правку —
ни одного профиля с функцией тяжелее 0,6 %. Весь оставшийся бюджет на нажатие —
250 мс debounce плюс ~12 мс приложенческой работы вне компиляции и загрузки
обновления DOM, редактор и дерево контролов. Следующий рычаг нужно выбирать
между политикой debounce (пользовательский компромисс «чувствительность против
лишних компайлов») и контрактом `FORMA-TEMPLATES-2` с общим телом шаблона для
повторов; ничего из этого не начинаем без явного решения.

Ограничения замера: профайл — один прогон по 10 нажатий, не пара A/B (повторный
запуск завис на ожидании мутации статуса после правки и был остановлен, поэтому
в архиве лежит первая, воспроизведённая по драйверу версия); сравнение Node/браузер
снималось на одной машине и одной сборке wasm с включённым кэшем разбора, для
другого контракта его надо переснять.

## Заимствование токенов в разборе документа (Rust, `bd3b304`)

Атрибуция остатка нативной загрузки (`vector-ui/examples/runtime_load_phases.rs`,
фикстура 256 контролов): `Runtime::from_sources` стоил 64 847 аллокаций на компилейт,

в `String` каждый идентификатор и каждый hex-цвет, `expect(Kind::Ident("…".into()))`
аллоцировал константу на каждую проверку, а `seen`/`specified`/`colors`/`numbers`

не изменились.

79 → 38 аллокаций на контрол, вся загрузка 64 847 → 54 340 аллокаций (−16 %),
запрошенные байты на загрузку 4 547 486 → 4 327 229 (−5 %). В настоящем WASM (Node,
три чередующиеся пары, `load_component` на нажатие с правкой одного контрола из 256)
медианы 5,41 / 4,94 / 5,10 → 4,65 / 4,89 / 4,71 мс (−8 %), на 32 контролах
0,87 / 0,86 / 0,82 → 0,84 / 0,77 / 0,76 мс. Дайджесты `DisplayList` на 1/32/256
совпали с ранее снятыми, пиксели 900×600 идентичны обеим сборкам (`edab4d6b52948a5d`),
байты транспорта тоже.

## Лишний клон спеки на лист-сцене загрузки (Rust)

Атрибуция фаз из предыдущей секции показала, что кроме токенов и выдачи `Template`
загрузка платит за три глубоких клона `ButtonSpec` на контрол. Один из них оказался
лишним: `Runtime::from_sources` собирал для каждого контрола «лист-сцену» и писал
одну и ту же спеку дважды — в `button` и в `buttons: vec![spec.clone()]`. Поле

## Разбор документа сканирует байты, а не символы (Rust, `1ec1b29`)

`Lexer::peek()` возвращал следующий символ как `source[offset..].chars().next()`, а `bump()`
звал `peek()` второй раз: каждый байт пробела, комментария, имени свойства и цифры стоил
срез и UTF-8-декодирование. Пробелы и комментарии теперь проходятся побайтово, как и
ограниченные ASCII сканы `#hex`, имени и числа (включая суффиксы `ms`/`px`); символ
декодируется только внутри строковых литералов и там, где байт `0x80..` может быть значим.
Разбор 256-контрольного документа — 409 433 → 222 350…242 208 нс (−41…−46 %) при тех же
523 аллокациях, вся нативная загрузка — 657 174 → 500 117…539 150 нс (−18…−24 %).
В реальном WASM это нажатие 256 контролов 3,51 → 3,31 мс (−5,7 %, 5 побед из 6 пар) и
32 контрола 0,56 → 0,53 мс (−5,4 %, 5/6): правка трогает разбор документа, на который
кэш разбора шаблонов не распространяется. `firstMs` (холодная загрузка) и `steady` на 256
остались в шуме (−0,6 % и −2,1 % при 3/6 и 4/6). Браузер выигрыш не разрешает: изолированный
компиляйт 256 контролов 10,1/10,2 мс против 10,8/9,4 мс при шуме ±1,5 мс, Studio стартует,
статус `Live preview обновлён`. Эквивалентность держится: дайджесты `DisplayList`
1375888489770191918 / 4896571815845383841 / 2260981288911909770, пиксели
`edab4d6b52948a5d` (`FORMASAMPLES=5`) во всех восьми парах, транспорт 219 760 и 1 758 124
байта, `forma.js` байт-в-байт тот же, 145 нативных и 269 из 270 JS-тестов, все семь
каналов `compile-digest.mjs` совпадают. Логи:
`.forma/verification/pipeline/2026-09-25-lexer-byte-scan/`.

Дальше в этом пути по профилю (`sample`, 9 089 сэмплов) остаётся только ровное
распределение: листья lexer'а — `starts_with` 299, `bump` 331, `skip_bytes` 216,
`str::parse::<f32>` 187, рост `Vec<ButtonSpec>` 113, а `_platform_memcmp` во всём
профиле 148 сэмплов (1,6 %), то есть сведение трёх проходов сверки имён свойств в один
switch оправдания не имеет.

Заодно замерены и закрыты две ветки. Растр: `pixels(900,600,1)` — 0,15/0,09/0,14 мс на
1/32/256 контролах, `tick` — до 0,015 мс, то есть paint-путь раннера дешевле загрузки на
порядок и рычагом не является. А главный остаток WASM-нажатия — не Rust, а переправа
транспорта: `TextEncoder().encode()` на 79 048 + 1 758 116 байт стоит 1,545 мс из 3,31 мс
`load_component` (47 %), при 0,138 мс на простое побайтовое копирование тех же буферов.
Значит `FORMA-TEMPLATES-2` (общее тело шаблона вместо 6 821 байт повтора на контрол) или
инкрементальная передача изменённого куска внутри wasm-памяти — единственный крупный
рычаг нажатия; оба меняют публичный API предпросмотра и остаются решениями пользователя.

## GPU-транспорт на каждое нажатие дороже самой загрузки (замер, `b668884`)

Рендер-путь браузера раньше был замерен только со стороны CPU-растра. На самом деле при
GPU-бэкенде (`src/vector-gpu.js`) `content_pixels` вообще не вызывается (`if(gpu)return image`),
а каждый кадр просит у модели `gpu_commands` / `gpu_edges` / `gpu_tiles`. Так как предпросмотр
создаёт новый `Runtime` на каждую компиляцию, проверка `modelKey!==model` в `changed`
срабатывает всегда, и эти вызовы приходят на модель, где список отображения ещё не построен:
сама сборка `DisplayList` живёт внутри первого `gpu_commands`, а не внутри `load_component`.

Два новых случая в `runtime_load_phases` (256 контролов, нативно, fat LTO):

| случай | время | аллокации | запрошено байт |
|---|---|---|---|
| `full_from_sources` (загрузка) | 372 350 нс | 811 | 491 497 |
| `gpu_transport_new_model` (загрузка + команды + рёбра + тайлы) | 1 644 150 нс | 7 044 | 25 749 489 |
| `gpu_transport_warm` (те же вызовы на готовой модели) | 84 792 нс | 19 | 4 389 240 |

То есть сборка транспорта стоит ~1,27 мс и 6 233 аллокаций против 0,37 мс и 811 у всей
загрузки, а повторные запросы на нагретой модели — это уже просто копирование 4,4 МБ
(клоны `commands` и `edges` в `runtime.rs:968-979`). В настоящем WASM (`.forma/…/gpu-transport-bench.mjs`,
модель новая каждый раунд, масштаб 1, 900×600) нажатие 256 контролов: загрузка 3,34 мс и
транспорт 2,88 мс из них `gpu_commands` 2,60 мс (буфер 1 527 200 байт), `gpu_edges` 0,18 мс
(1 799 536 байт), тайлы/пейнты/параметры 0,10 мс; на 32 контролах 0,79 мс против 0,49 мс.
CPU-растр при этом 0,09…0,15 мс, `tick` ≤ 0,015 мс, так что «paint» в этом проекте —
не растеризация, а сборка и переправа геометрии.

Что из этого следует (по порядку цены, всё — решения пользователя, а не самостоятельные правки):
первым делом отменять пересборку транспорта на неизменившейся геометрии, то есть либо
переиспользовать одну модель между компиляциями вместо нового `Runtime` на нажатие, либо
кэшировать сборку `DisplayList` по содержимому так же, как кэшируется разбор шаблона;
второе — убрать клоны 4,4 МБ (`gpu_commands`/`gpu_edges` клонируют весь буфер); третье —
объём транспорта (`FORMA-TEMPLATES-2`). Логи: `.forma/verification/pipeline/2026-09-25-lexer-byte-scan/`
(`phases-gpu-transport.txt`, `gpu-transport-bench.mjs` + `.txt`).

## Буферы сцены выделяются одного размера, а не удвоением (Rust, `2a0d4ec`)

Замер транспорта из предыдущего раздела разложился по аллокатору: из 1,64 мс и 25,7 МБ на новую
модель 96 % всех `realloc` и 19,8 из 22,8 МБ запрошенных байт — это рост
буферов удвоением внутри сборки `DisplayList`, а не полезная работа. 256 детских списков и один
слитый список сцены наращивались с нуля, хотя итог — 3,33 МБ; каждый контрол к тому же начинал
с собственного пустого скача для флэттенга глифов. Профилировщик здесь бессилен: после fat LTO
93 % сэмплов лежат в `main`.

Правка (`vector-ui/src/display_list.rs`, `vector-ui/src/runtime.rs`): сцена строит детские списки
до слияния, поэтому второй и каждый следующий контрол получает подсказку ёмкости от соседа и
выделяется одним `with_capacity`; слитый буфер резервируется точно по сумме детей плюс семь записей
самой сцены; скач флэттенга один на всю сборку; тайлер резервирует `ranges` по числу команд и
урезает хвост `data` по уже посчитанным длинам. Подсказки не попадают в байты — неточная оценка
означает рост вектора или запас, но не другие команды.

Итог: на 256 контролах транспорт новой модели — 200 `realloc` вместо 5 233 (−96 %),
12 816 513 байт вместо 25 749 489 (−50 %), 1 757 аллокаций вместо 7 044 (−75 %), медиана
1,99 → 1,58 мс (все три замера «после» ниже трёх «до»); на 32 контролах 689 → 58 `realloc`,
3,20 → 1,57 МБ, медиана 387 → 241 мкс. В настоящем WASM, где оба пакета живут в одном
Node-процессе и порядок сторон чередуется каждый сэмпл (`wasm-paired-ab.mjs`), транспорт 256
контролов — 2,644 → 2,437 и 2,678 → 2,491 мс (21 из 28 пар лучше), 32 контрола −11…−12 %,
а сцена из одного контрола не меняется вовсе (она не сливает списки). Целый нажим
(загрузка + транспорт) на 256 контролах — 6,10 → 5,82 и 6,52 → 6,13 мс.

Эквивалентность: digests `DisplayList` 1/32/256 не изменились, `uploadBytes` и `payloadSha` на
каждый сэмпл совпадают между пакетами, `pixelSha` CPU-растра тот же, `forma.js` байт-идентичен,
`cargo test --release --locked` — 145 зелёных, `gpu_check` с feature `gpu` проходит,
`compile-digest` — `sessionMatchesCold`, `npm test` — 269/270 с той же единственной известной
поломкой. Загрузочный путь не тронут: 811 аллокаций и 491 497 байт как до, так и после, поэтому
`runtime_load_phases` теперь печатает `reallocs_per_op` отдельным полем — именно оно показывало
причину. Логи: `.forma/verification/pipeline/2026-09-25-transport-capacity/`
(`native-capacity-ab.sh` + `.txt`, `wasm-paired-ab.mjs` + `.txt`, `README.md`).

Осталось 12,8 МБ запросов — это сами итоговые буферы (детские и слитый списки плюс клон для
`gpu_commands`), а не трафик роста. Его убирают только два следующих шага, и оба — решения
пользователя: отказ от клонов в `gpu_commands`/`gpu_edges` и переиспользование одной модели между
компиляциями.

Подсказку соседа отдельно проверили на сцене, где размеры контролов чередуются (каждая вторая метка —
140 символов): там выигрыш меньше, но тоже большой — 6 377 → 1 334 `realloc` (−79 %), 74,90 → 44,83 МБ
запросов (−40 %), 40,89 → 35,78 МБ живой памяти. Перебора ёмкости нет ни в равномерной, ни в смешной
сцене, поэтому гейт «хинтовать только одинаковым по шаблону контролам» не добавлен. Та же смешная сцена стоит
9,06 МБ полезной нагрузки против 3,17 МБ: разнообразие текстов дороже, чем однотипные контролы, и это
настоящая работа по флэттенингу глифов (там же — и причина, по которой мемоизация формы глифа не
проходит: она не байт-точна). Логи и временные инструменты аудита:
`.forma/verification/pipeline/2026-09-25-transport-capacity/` (`mixed-fixture.mjs`,
`hint_reserve_audit.rs`, раздел «Аудит запаса» в `README.md`).

Гарантия от возврата: тест `transport_sizes_control_buffers_instead_of_growing_them`
(`vector-ui/tests/runtime_allocations.rs`) считает попытки аллокации вокруг целого транспорта новой
модели на 128 контролах и держит бюджет 28 аллокаций на контрол для сцены с длинными подписями. На
сборке до правки он падает (5 634 попытки вместо 3 064), на текущей проходит; весь нативный прогон —
146 тестов зелёные.

## Транспорт разложен по фазам: осталась сборка геометрии (Rust, `a1a67f7`)

Замер по фазам на 256 контролах: из ~1,6 мс транспорта новой модели на сборку `DisplayList` уходит
1,42–2,09 мс, на клоны ради API (`gpu_commands` + `gpu_edges`) — 20–30 мкс (~1,4 %), на тайлер
900×600 — 41–56 мкс (~3 %). То есть копирования и тайлинг больше не мишень: дальше складывается
ся в работу по флэттенингу кривых, а 3,25 МБ клонов и переиспользование одной модели — решения
пользователя.

Мелкая правка внутри сборки текста: `vector_glyphs` мерил ширину подписи через `measure_text` и затем
заново разрешал те же символы для каждого контура, т. е. платил поиском в cmap и в таблицу смещений
дважды на символ. Теперь идентификаторы собираются за один проход (`glyph_ids`), а арифметика ширины
вынесена в общий `pixels_from_units`, чтобы суммы совпадали бит в бит. Результат: на смешной сцене с
140-символьными метками сборка геометрии −3 % по медиане (6,76–7,44 → 6,69–7,21 мс за 7 чередующихся
раундов), на равномерной фикстуре эффект не различим; аллокаций чуть больше (+2 и +7 — буфер
идентикаторов). Эквивалентность подтверждена digests 1/32/256, тестом точности потоковой сборки
(`streamed_glyphs_preserve_exact_geometry_and_coverage`), 146 зелёными нативными тестами, `gpu_check`,
байт-идентичным `forma.js` и `pixelSha edab4d6b52948a5d` в настоящем WASM. Логи:
`.forma/verification/pipeline/2026-09-25-transport-capacity/` (`native-glyph-lookup-ab.txt`,
`native-glyph-lookup-rounds2.txt`, раздел «Разбор транспорта по фазам» в `README.md`).

## Остаток «40 аллокаций в кадр» закрыт: это фиксированная цена вызова, не Forma (замер)

Два сценария выше оставляли открытый вопрос из более ранних секций («требуется атрибуция»,
«требуют stack attribution»): 32 аллокации в кадр в статике и 40 в анимации лежали внутри
`draw`/`submit`, но два размера сцены (100 и 256) не различали работу Forma на контрол и
постоянные издержки одного вызова wgpu. В `gpu_scene_bench` добавлен `FORMA_BENCH_CONTROLS`
(список размеров сцены, по умолчанию `100,256`), и замер повторён на 1, 2 и 100 контролах, 200
кадров, без timestamps:
- статика (изменений красок нет, `paint_bytes/frame=0`): `[pointer, draw-submit, wait]= [0, 6400, 0]`
  то есть ровно 32/кадр при 1, 2 и 100 контролах; трафик 1 460 000/1 462 400/1 467 200 байт за
  серию, т. е. ~7 300 байт и ~228 байт на аллокацию — поштучные объекты вызова, не payload;
  между 1 и 100 контролами общий объём меняется на ~36 байт/кадр, так что за кадр большой массив
  команд не копируется;
- анимация: 40/кадр (8000 за серию) тоже одинаково при 1, 2 и 100 контролах, хотя payload красок
  различается в сто раз (32 против 3 200 байт/кадр) — восемь штук относятся к пути записи
  изменившегося диапазона красок, а не к его размеру.
Всезде 0 реаллокаций, live-байты до и после одинаковы, 0 новых буферов и 0 геометрийных загрузок,
прогретая подготовка сцены — 0 аллокаций. Вывод: остаток — постоянные издержки encoding/submit
внутри wgpu; вклад структур Forma в кадр измерим как ноль (pointer, подготовка, wait/readback).
Сократить эти восемь можно только убрав отдельную загрузку красок (Рычаг — решение пользователя,
см. предыдущую секцию), и что именно из них тогда уйдёт, надо мерить, а не предполагать. Ограничения:
счётчик process-wide и видит только Rust (Objective-C/Metal невидимы), stack-профиля нет,
промежуточные размеры сцены не проверялись, 200 кадров offscreen с синхронным ожиданием — не soak
окна и не тест утечек. Скорость тут не заявляется: цена кадра в этом сценарии на GPU-стороне
(GPU p50 1,23/1,58 мс на 100/256 контролах). Лог:
`.forma/verification/pipeline/2026-09-25-transport-capacity/native-fixed-per-frame-floor.txt`.

## Гейт `npm test` починен: падение `version command` был симлинк, а не Forma (правка)

Все секции этой пачки честно носили приписку «269 из 270, падает только предсуществующий
`version command updates only its component and all associated lockfiles`». Причина найдена и
закрыта: тест копирует `scripts/versions.mjs` во временную папку, macOS отдаёт её путь через
симлинк (`/var` → `/private/var`), а guard входа в CLI сравнивал «путь из argv» и «путь модуля» как
