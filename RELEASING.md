# CI и версии Forma

Один репозиторий, два независимо выпускаемых компонента. Версии не обязаны
совпадать. Коммит может получить оба тега, если выпускаются оба компонента.
Текущие `0.1.0` в manifest — начальные версии; опубликованных тегов пока нет.

| Компонент | Где хранится версия | Релизный тег | Артефакт GitHub Release |
|---|---|---|---|
| Forma (библиотека Rust + WASM) | `vector-ui/Cargo.toml` + Cargo.lock | `forma-v0.1.0` | `forma-0.1.0-wasm.tar.gz` |
| Studio | `package.json` + package-lock.json | `studio-v0.1.0` | `forma-studio-0.1.0-web.tar.gz` |

`native-app` — вспомогательный WebView-хост Studio, его версия синхронизируется
со Studio. Это не третий независимо выпускаемый продукт. Нативный векторный
пример в `vector-ui` относится к библиотеке Forma. Rust crate и demo-бинарник
называются `forma`; WASM-архив содержит `forma.js` и `forma_bg.wasm`.
Внутреннее имя компонента в командах и metadata остаётся `runtime`.

Manifest хранит версию разработки. Тег фиксирует конкретный выпуск. Версия
не выводится из количества коммитов; каждому промежуточному коммиту не нужен
новый номер. Выпущенные теги не перемещаем и не перезаписываем: исправление
выходит новым номером. Непрефиксные `v0.1.0` не используются, чтобы не смешивать
истории двух компонентов.

## Что повышать

- Исправление renderer, Rust parser, WASM API — Runtime.
- Изменение редактора, инспектора, MCP, интерфейса Studio — Studio.
- Изменение формата обмена JS ↔ Rust/WASM — оба компонента.
- Только документация/CI — обычно без повышения продуктовой версии.

Пока API экспериментальный (`0.x`), совместимые исправления повышают patch,
новые возможности/несовместимые изменения — minor. Стабильный публичный контракт
позже обозначим `1.0.0`. Для предварительных выпусков поддерживаются, например,
`forma-v0.2.0-rc.1` и `studio-v0.3.0-beta.2`; GitHub помечает их prerelease.
Build metadata (`+...`) в номерах релизов не используем; для идентификации
сборки служит SHA коммита.

Studio всегда собирает и включает WASM из того же checkout. В
`dist/vector-pkg/build-info.json` записаны версии Runtime и Studio, версия
wasm-bindgen, SHA и признак незакоммиченных изменений. CI пакует только чистый
checkout. Не подкачиваем «последний Runtime» во время сборки или открытия Studio.
Это фиксирует проверенную пару, пока мы не определили самостоятельный стабильный
протокол совместимости Studio ↔ Runtime.

## CI

`.github/workflows/ci.yml` запускается на PR, push в `main` и вручную:

- Ubuntu 24.04, macOS 15, Windows 2022: Rust unit/integration tests с `gpu`,
  проверка компиляции нативного векторного окна.
- macOS: проверка старого WebView-хоста Studio с явным тестовым `actions.rs`.
- Ubuntu: `npm ci`, проверка manifest/lockfile, сборка WASM, JS-тесты с настоящим
  WASM, production Studio, упаковка двух архивов и SHA-256.
- Артефакт Actions `release-bundles` хранится 14 дней; для PR это сборки проверки,
  а не опубликованные релизы.

Rust закреплён в `rust-toolchain.toml` (1.97.1), Node в `.node-version`
(22.23.2). CLI wasm-bindgen должен в точности соответствовать зависимости
Runtime (сейчас 0.2.125). Версии GitHub Actions закреплены полными SHA:
[checkout](https://github.com/actions/checkout),
[setup-node](https://github.com/actions/setup-node),
[cache](https://github.com/actions/cache),
[upload-artifact](https://github.com/actions/upload-artifact).

Тесты с реальным GPU остаются `#[ignore]` и запускаются отдельно на машине
с подходящим adapter:

```sh
cargo test --locked --manifest-path vector-ui/Cargo.toml --features gpu -- --ignored
```

Обычный CI не выдаёт отсутствие GPU за успешную аппаратную проверку. Замеры
FPS/latency также не являются блокирующей частью общей матрицы: для них нужны
сопоставимые условия. Для сравнения со старыми бенчмарками на Rust 1.99 nightly
нужна такая же версия компилятора либо новый baseline на закреплённом toolchain.

После первого удалённого прогона рекомендуется сделать проверки `Runtime / …`
и `Studio + actual WASM` обязательными для слияния в `main`. Правила защиты
ветки и удалённые настройки GitHub в этом изменении не меняются.

## Подготовка и выпуск

Команда обновляет manifest и связанные lockfile, не создавая коммит или тег:

```sh
npm run version:set -- runtime 0.2.0
# либо
npm run version:set -- studio 0.2.0
npm run version:check
```

Для Studio команда также обновляет версию `native-app`. Поэтому обычный
`npm version` отдельно от этой команды использовать не следует: он не знает
о Rust-хосте. Номера выбираются вручную; автоматического повышения по сообщениям
коммитов пока нет.

Дальше закоммить изменения, дождись CI и слей их в `main`. На нужном коммите:

```sh
npm run version:check -- forma-v0.2.0

git tag -a forma-v0.2.0 -m "Forma 0.2.0"
git push origin forma-v0.2.0
```

Для Studio аналогично `studio-v0.2.0`. Начальный релиз без повышения текущих
manifest может использовать `forma-v0.1.0` / `studio-v0.1.0`.

**Push тега — команда публикации.** `.github/workflows/release.yml` сначала
проверяет номер тега, затем заново запускает весь CI для этого коммита. Только
после успеха всех jobs он скачивает архивы из этого же запуска, проверяет
SHA-256 и создаёт GitHub Release выбранного компонента. Ничего не пересобирается
между проверкой и публикацией. Ошибка любого обязательного job блокирует выпуск.
Существующий Release не перезаписывается. Общая метка GitHub `Latest` не меняется,
поскольку у двух компонентов разные истории выпусков.

Публикации в crates.io/npm и установки глобальных пакетов нет. Rust-библиотеку
можно будет подключать к зафиксированному тегу репозитория после его выпуска:

```toml
[dependencies]
forma = { git = "https://github.com/themoretheless/forma", tag = "forma-v0.1.0" }
```

В коде библиотека импортируется как `use forma::Runtime;`. Этот пример
git-зависимости работает после появления тега. Перед crates.io нужно отдельно
определить лицензию, состав публичного пакета и контракт API.

Studio-архив — статическая web-сборка. Запуск локального Rust, native-окон и MCP
требует dev-server из исходников; эти возможности не появляются у статического
архива. Native installers/подпись/notarization в эту схему пока не входят.

## Локальная проверка

```sh
npm ci
cargo install wasm-bindgen-cli --version 0.2.125 --locked
npm run build:wasm
npm test
npm run build
npm run package:release
```

Архивы появляются в игнорируемой `.release/`. Локальные архивы могут иметь
`dirty: true` в metadata — это сборки разработки. Workflow на GitHub не
публикует такую сборку. Linux/Windows и сам удалённый workflow подтверждаются
первым запуском GitHub Actions; локальная проверка macOS их не заменяет.
